# Liara SRE Agent 🛠️
دستیار هوشمند راه‌اندازی، دیپلوی و پایش وب‌سایت روی لیارا: **رابط وب** + CLI + سرور MCP.
نمونه‌ی اولیه (MVP) برای چالش لیارا. **این README صادقانه می‌گوید چه چیزی تأیید شده و چه چیزی نشده.**

## چه کار می‌کند؟ (کنترل کامل پنل لیارا)
با چت فارسی ساده:
- **اپ‌ها:** ساخت/حذف، روشن/خاموش (`scale`)، ری‌استارت، تغییر پلن، متغیر محیطی (تنظیم/حذف)،
  تنظیمات (zero-downtime، ساب‌دامنه پیش‌فرض، IP ثابت، read-only)، دیسک و بکاپ دیسک، رویدادها و ریلیزها.
- **دیتابیس‌ها (DBaaS):** فهرست و جزئیات (بدون رمز)، ساخت/حذف، **خاموش/روشن**، تغییر پلن،
  بکاپ + لینک دانلود، شبکه‌ی عمومی، پنل مدیریت وب، متریک و رویدادها. مثلاً: «دیتابیس shop-db را خاموش کن».
- **دامنه‌ها:** فهرست، افزودن و اتصال به اپ، بررسی وضعیت، فعال/غیرفعال کردن SSL، ریدایرکت، حذف.
- **عیب‌یابی و پایش زنده:** امتیاز سلامت، نمودار CPU/RAM از تاریخچه‌ی واقعی API، هشدارها، تاریخچه‌ی اقدامات.

همه‌ی عملیات پرریسک (هر تغییر وضعیت/حذف/ساخت) فقط با کارت تأییدِ کاربر اجرا می‌شوند و در تاریخچه ثبت می‌شوند.

## ⚠️ وضعیت صداقت (مهم)
- **هیچ‌کدام از قابلیت‌ها روی اکانت واقعی لیارا آزمایش نشده است.** تست‌ها فقط با `MockClient` و یک «سرور جعلی» انجام شده‌اند که *قرارداد مستندات رسمی* را شبیه‌سازی می‌کند؛ این‌ها ثابت نمی‌کنند لیارای واقعی همان‌طور پاسخ می‌دهد.
- حالت `--mock` داده‌ی **شبیه‌سازی‌شده** نشان می‌دهد (در UI با نشان «حالت دمو» و در نتیجه‌ها با «شبیه‌سازی» مشخص شده).
- چت با LLM، سرور MCP، CLI (`rich`) و ظاهر/انیمیشن UI در مرورگر در محیط توسعه **اجرا نشده‌اند** (فقط کامپایل/بررسی نحو).

## معماری
```
 مرورگر (UI) ─┐                                   ┌─► client.py ──► API لیارا (فقط مسیرهای مستند)
 CLI چت/doctor├─► tools.py (ابزار + ریسک + اعتبارسنجی) ┤
 MCP ─────────┘        │  security.py (SSRF، اعتبارسنجی، تأیید یک‌بارمصرف)
                       ├─► diagnose.py (قواعد روی لاگ/منابع واقعی)   └─► Liara CLI (فقط برای دیپلوی)
                       └─► brain.py (گفتگو؛ LLM اختیاری) · server.py (وب‌سرور محلی) · audit.py
```
- **داده فقط از منبع واقعی:** وضعیت/پلن/scale/isDeployed از `GET /v1/projects/{name}`، لاگ از `…/logs`. اگر متریک در دسترس نباشد، CPU/RAM «نامشخص» نمایش داده می‌شود و هیچ عددی ساخته نمی‌شود؛ هر گزارش `sources` دارد (ok / unavailable + دلیل).
- **برچسب‌گذاری:** `recommend_plan`، `detect_project` (تخمین محلی)، `deploy_guide` و `domain_guide` (راهنمای ثابت) صراحتاً داده‌ی لیارا نیستند.

## تطبیق با API رسمی لیارا
منبع: فایل‌های خام OpenAPI در `liara-cloud/openapi/spec/{paas,dbaas,me}.yaml` (خوانده‌شده به‌طور کامل)
و https://developers.liara.ir. هر متد+مسیر از همین specها برداشته شده؛ تنها مسیرِ خارج از spec
(`GET /v1/networks`) پیش‌فرض غیرفعال است (`verified=False`؛ فقط با `LIARA_ALLOW_UNVERIFIED=1`).

| بخش | مسیرها (همه ✅ مستند در OpenAPI رسمی) |
|---|---|
| اپ‌ها | `GET/POST /v1/projects`، `GET/DELETE /v1/projects/{name}`، `POST …/actions/{restart,scale}` (`{scale:0|1}`)، `POST …/resize`، `POST /v1/projects/update-envs`، `GET …/logs?since=`، `GET …/{events,releases,metrics/summary,metrics/{cpu,memory,…}}`، `…/disks` + بکاپ/دانلود بکاپ، تنظیمات `…/{id}/{zero-downtime,default-subdomain,fixed-ip,read-only}/{enable,disable}` |
| دیتابیس‌ها | `GET/POST /v1/databases`، `GET/DELETE /v1/databases/{id}`، `POST …/actions/scale` (خاموش/روشن)، `POST …/resize`، `GET/POST …/backups`، `POST …/backups/{name}/download`، `PATCH …/public-network/{enable,disable}`، `POST …/control-panel/{enable,disable}`، `GET …/metrics/summary`، `GET …/events` |
| دامنه‌ها | `GET/POST /v1/domains`، `POST /v1/domains/set-project`، `GET /v1/domains/{id}/check`، `POST /v1/domains/provision-ssl-certs`، `POST …/{id}/ssl/disable`، `POST …/{id}/set-redirect`، `DELETE …/{id}` |
| حساب و پلن‌ها | `GET /v1/me` ← کاربر + `plans.{projects,databases}` (کاتالوگ پلن‌ها با CPU/RAM/قیمت) + `defaultDatabaseVersions`؛ پاسخ ۱۰ دقیقه کش می‌شود |
| دیپلوی | با **Liara CLI** (بدون تغییر نسبت به قبل) |

نکته‌های رفتاری مهم:
- **`update-envs` جایگزینی کامل است**: قبل از ثبت، متغیرهای فعلی از جزئیات اپ خوانده و merge می‌شوند تا چیزی پاک نشود.
- **وضعیت اجرا**: API واقعی برای اپ سالم `status="ACTIVE"` می‌دهد. تشخیص وضعیت (`diagnose.app_state`)
  ترکیبی از `status` و `scale` است و وضعیت ناشناخته را «خاموش» فرض نمی‌کند (باگ قبلیِ هشدار کاذب «اپ در حال اجرا نیست» رفع شد).
- **رمز دیتابیس** (`root_password` در پاسخ DBaaS) در لایه‌ی ابزار حذف می‌شود و هرگز به UI/LLM نمی‌رسد.

### فلگ‌های Liara CLI
`liara deploy --app --platform --port --path --no-app-logs` (از کد/مستندات CLI). توکن از **متغیر محیطی** `LIARA_API_TOKEN` به پردازش CLI داده می‌شود (نه آرگومان). ⚠️ اینکه CLI این متغیر را بخواند تأیید نشده؛ اگر نخواند احراز هویت ناموفق می‌شود (امن است) و باید `liara login` انجام شود.

### قالب `metrics/summary` و رفتار `normalize_metrics`
ساختار رسمی: `cpuUsage` و `memoryUsage` = آرایه‌ای از `{applet, value}` و `disksUsage` = آرایه‌ای از `{name, size, usage, reportedAt}`. `normalize_metrics` همچنان `{cpu, memory, disk}` برمی‌گرداند و:
- `value` را هم به‌صورت یک جفت `[timestamp, value]` و هم فهرستی از جفت‌ها می‌پذیرد و **جدیدترین نمونه** را برمی‌دارد؛ مقدار رشته‌ای عددی (مثل `"0.25"`) پذیرفته می‌شود.
- NaN/inf، منفی، bool، رشته‌ی غیرعددی، جفت ناقص و دیسک با `size=0` **نادیده گرفته** و در `issues` گزارش می‌شوند؛ هیچ مقداری ساخته نمی‌شود.
- پاسخ خالی/ناشناخته ← `get_metrics` خطای قابل‌فهم می‌دهد و در `diagnose_app` منبع متریک `unavailable: …` می‌شود.
- دیسک از `usage/size` درصد می‌شود (مستقل از واحد). در قالب رسمی، مقادیر CPU بر حسب **هسته** و RAM بر حسب **بایت** گزارش می‌شوند (رفتار مشاهده‌شده‌ی API؛ مجموع اپلت‌ها). درصد CPU/RAM **فقط نسبت به سقف پلنِ همان اپ از کاتالوگ `/v1/me`** محاسبه می‌شود (`metrics_detail`)؛ اگر پلن در کاتالوگ پیدا نشود درصد ساخته نمی‌شود و مقدار خام خوانا (هسته/MB) نمایش داده می‌شود. نمودار هم با سری زمانی واقعی `metrics/{cpu,memory}?since=` پر می‌شود، نه نمونه‌ی ساختگی. (قالب قدیمیِ درصدیِ `cpu/memory/disk`، که دمو استفاده می‌کند، همچنان پشتیبانی می‌شود.)

### ابهام مستندات
- **آدرس پایه:** spec رسمی `https://api.liara.ir` است و همان پیش‌فرض فعلی کد است (`LIARA_API_BASE_URL` قابل‌تنظیم، فقط `https://*.liara.ir`).
- **واحد `metrics/summary`:** در spec واحد نوشته نشده؛ از رفتار API (و کدهای متن‌بازِ تست‌شده روی لیارای واقعی) مقدار RAM بایت و CPU هسته است. به همین دلیل درصد فقط با سقف پلن ساخته می‌شود و اگر پلن معلوم نباشد، همان مقدار خام نشان داده می‌شود — عددی حدس زده نمی‌شود. اگر لیارا واحد را عوض کند، درصدها غلط می‌شوند ولی مقدار خام همچنان نمایش داده شده و کنار درصد دیده می‌شود.
- **`status` اپ/دیتابیس:** فهرست مقادیر مستند نیست؛ نگاشت وضعیت (`diagnose.app_state`) دفاعی است (ACTIVE/RUNNING/READY=در حال اجرا، scale=0=خاموش، ناشناخته+scale≥1=در حال اجرا، وگرنه «نامشخص» بدون جریمه‌ی امتیاز).
- **`GET /v1/databases/{name}/events`:** در spec پارامتر مسیر `name` است؛ ما hostname (و در نبودش id) می‌فرستیم.
- **`update-envs`:** معنای جایگزینی کامل از رفتار API برداشت شده، نه از متن spec؛ برای همین merge سمت ما محافظه‌کارانه است (خواندن همه‌ی متغیرها و ارسال مجموعه‌ی کامل).
- تست‌ها همچنان با `MockClient` و سرور جعلیِ مبتنی بر spec اجرا می‌شوند و روی اکانت واقعی لیارا آزمایش نشده‌اند.

## امنیت
- **توکن:** فقط از env؛ در هیچ آرگومان/URL/لاگ/audit/خروجی نمی‌آید (پاک‌سازی `Bearer …` و خود توکن). آدرس پایه فقط `https://*.liara.ir` است (جلوگیری از ارسال توکن به سرور دیگر).
- **وب‌سرور:** فقط `127.0.0.1`؛ بررسی `Host` (ضدّ DNS-rebinding) و `Origin`؛ توکن نشست تصادفی برای همه‌ی `/api`؛ فقط `application/json`؛ سقف بدنه ۶۴KB؛ محدودیت ۳۰ پیام در دقیقه؛ CSP با nonce، `X-Frame-Options: DENY`، `nosniff`.
- **تأیید عملیات حساس:** ری‌استارت، تغییر پلن/env و دیپلوی بدون تأیید اجرا نمی‌شوند. تأیید یک‌بارمصرف، زمان‌دار (۵ دقیقه)، با شناسه‌ی تصادفی؛ پارامترها سمت سرور نگه داشته می‌شوند و کلاینت نمی‌تواند تغییرشان دهد؛ فقط `approve === true` پذیرفته می‌شود. هر تصمیم در `audit.jsonl` ثبت می‌شود.
- **SSRF:** تست سلامت سایت فقط `http/https`، پورت ۸۰/۴۴۳، بدون user:pass، فقط IP عمومی (رد loopback/private/link-local/metadata/CGNAT/IPv4-mapped)، اتصال مستقیم به IP حل‌شده (ضدّ DNS-rebinding)، بدون دنبال‌کردن ریدایرکت. کلون فقط از `https://github.com/user/repo`.
- **اعتبارسنجی ورودی:** نام اپ، شناسه‌ی پلن، پلتفرم، پورت، نام/مقدار env، دامنه و مسیرها (تحلیل/دیپلوی فقط داخل `LIARA_PROJECT_PATH`). مقادیر env هرگز نمایش داده نمی‌شوند.
- **MCP:** پیش‌فرض فقط‌خواندنی؛ ابزارهای تغییردهنده فقط با `LIARA_MCP_ALLOW_MUTATIONS=1` و دومرحله‌ای با `confirmation_token`. ⚠️ MCP نمی‌تواند ثابت کند انسان واقعاً تأیید داده؛ به UI تأیید ابزار در کلاینت وابسته است.
- **تزریق از لاگ:** لاگ‌ها داده‌ی غیرقابل‌اعتماد به LLM داده می‌شوند و عملیات حساس همیشه تأیید انسانی می‌خواهد.

## راه‌اندازی
```bash
pip install -r requirements.txt           # هسته و وب بدون نصب هم کار می‌کنند (rich فقط برای CLI)
cp .env.example .env && export $(grep -v '^#' .env | xargs)   # یا متغیرها را دستی تنظیم کنید
```
اکانت واقعی: `LIARA_API_TOKEN` را بسازید (پنل لیارا ← API) و اجرا کنید:
```bash
python -m liara_agent web            # → http://127.0.0.1:8080
python -m liara_agent doctor <app>   # عیب‌یابی در ترمینال
python -m liara_agent chat           # چت هوشمند (نیازمند BOXAPI_API_KEY)
python -m liara_agent.mcp_server     # MCP (فقط‌خواندنی؛ برای تغییر: LIARA_MCP_ALLOW_MUTATIONS=1)
```
برای دیپلوی: نصب `@liara/cli` و `git`، و اپ مقصد باید از قبل در لیارا ساخته شده باشد.

## اجرای دمو (شبیه‌سازی‌شده)
```bash
python -m liara_agent web --mock     # بدون توکن و بدون اینترنت
```
۱) «ارور ۵۰۰ می‌دهد» ← هشدار، گزارش با منبع داده و کارت تأیید ← ۲) «تأیید» ← بررسی مجدد (RAM ۹۷٪ ← ۵۴٪؛ داده‌ی شبیه‌سازی‌شده) ← ۳) «https://github.com/acme/shop را دیپلوی کن» (نتیجه‌ی مراحل با برچسب شبیه‌سازی) ← ۴) «📋 تاریخچه اقدامات».

## تست
```bash
python tests/run.py        # بدون pytest؛ با pytest هم قابل‌اجراست
```
۴۴ تست: قالب رسمی/خالی/نامعتبر `metrics/summary` و تحلیل مصرف بالا، منطق عیب‌یابی/دیپلوی (Mock)، قرارداد کلاینت با سرور جعلی (مسیر/هدر/بدنه/خطاها/نشت توکن)، SSRF، اعتبارسنجی، تأیید عملیات، محافظ‌های وب‌سرور، نبود توکن در argv، پاک‌سازی audit، مدیریت خطا و نبود داده.

## محدودیت‌های شناخته‌شده
1. هیچ تستی روی لیارای واقعی انجام نشده؛ قالب پاسخ لاگ، فرمت `since`، قالب فهرست اپ‌ها و مقدار دقیق `status` تأیید نشده‌اند (تشخیص «در حال اجرا» با وجود `run` در متن `status`).
2. اگر متریک در دسترس/معتبر نباشد (یا واحد CPU/RAM نامشخص بماند)، تشخیص‌ها فقط بر پایه‌ی لاگ و وضعیت‌اند (اطمینان پایین‌تر) و پیشنهاد خودکار تغییر پلن ارائه نمی‌شود.
3. قواعد عیب‌یابی الگوهای متنی ثابت روی لاگ هستند؛ علت‌های ناشناخته را «نامشخص» گزارش می‌کند.
4. دیپلوی وابسته به Liara CLI، `git` و یک اپ ازپیش‌ساخته؛ مخزن‌های خصوصی و محدودیت حجم کلون پشتیبانی/اعمال نمی‌شود.
5. وضعیت اپ پس از دیپلوی حداکثر ~۶۰ ثانیه polling می‌شود؛ تست سلامت فقط زمانی انجام می‌شود که آدرس داده شود یا زیردامنه‌ی پیش‌فرض فعال باشد (`<app>.liara.run` فرض شده).
6. دامنه/ایرنیک فقط راهنمای ثابت است؛ تنظیم DNS/ایرنیک خارج از دسترس است.
7. پایش ۲۴ساعته وجود ندارد (طبق صورت چالش)؛ هشدارها و نمودار فقط وقتی پنل باز است به‌روز می‌شوند و نمودار فقط از نمونه‌های زنده ساخته می‌شود.
8. UI یک‌کاربره و محلی است (بدون احراز هویت چندکاربره).

## استقرار روی لیارا

مخزن شامل `Procfile` است و فرمان شروع برنامه `python -m liara_agent web` می‌باشد. در تنظیمات متغیرهای محیطی برنامه در لیارا این متغیرها را با مقادیر محرمانه تنظیم کنید:

- `LIARA_WEB_USERNAME`: نام کاربری دلخواه برای دسترسی به پنل وب.
- `LIARA_WEB_PASSWORD`: رمز عبور قوی و منحصربه‌فرد.

در محیط میزبانی، برنامه از متغیر `PORT` (در صورت وجود) استفاده می‌کند و روی `0.0.0.0` گوش می‌دهد. اگر حالت عمومی با `LIARA_PUBLIC=1` فعال شده باشد، احراز هویت نام کاربری/رمز عبور اجباری است و بدون این دو متغیر سرور عمداً شروع نمی‌شود. رمزها را در GitHub یا داخل کد قرار ندهید؛ فقط در تنظیمات محیطی پنل لیارا وارد کنید.

این تغییرات فقط مشکل bind/port و دسترسی HTTP را هدف می‌گیرند؛ اتصال به API واقعی لیارا و عملکرد کامل برنامه پس از استقرار باید جداگانه آزمایش شود.
